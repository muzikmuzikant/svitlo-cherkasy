# Світло Черкаси · Адміністративна система (АСКОД-подібний робочий простір)

> Робоча специфікація для гілки **staging**. Власний дизайн і функції, без копіювання торгової марки або вихідного коду АСКОД.
> Версія документа: 2026-10-21. Будь-які релізи у `main` лише після регресійних перевірок і окремого погодження.

## 1. Мета

Перетворити адмінпанель на повноцінне середовище управління, де більшість щоденних операцій не потребує GitHub, ручного редагування JSON, SQL або доступу до Railway Variables. Публікація контенту, зміни доступності функцій, звернення, підтверджені адресні уточнення та моніторинг керуються захищеним інтерфейсом і відповідними API. Власне програмний код, безпекові секрети, структура БД і нові модулі все ще потребують окремої розробки й розгортання.

## 2. Принципи інтерфейсу

- Широке робоче поле для комп'ютера, компактне мобільне відображення.
- Стійка ієрархія: робочий стіл → модуль → реєстр → картка → хід виконання.
- Ліва навігація у вигляді дерева, глобальний пошук та можливість закріплення розділів.
- Контекстні кнопки: створити, підготувати, підтвердити, опублікувати, відмінити, переглянути історію.
- Зміни збережено/не збережено, успіх і помилки завжди показуються текстом.
- Доступні форми з клавіатури, стан фокусу, м'які анімації з `prefers-reduced-motion`.
- Ніякого технічного жаргону або назв внутрішніх таблиць у користувацькому PWA.
- Дозволено надихатися патернами системи електронного документообігу, заборонено копіювати логотип чи стверджувати офіційний зв'язок з АСКОД.

## 3. Уже реалізовано в staging

- `admin-system.js`, `admin-system.css`: оформлення робочого простору, картотека завдань, модуль оперативних налаштувань.
- `push-server/work-registry.js`: збережений у Railway реєстр робіт з номером `WR-...`, виконавцем, пріоритетом, статусом, контрольним терміном і слідом редагувань.
- `/api/admin/work-items`: авторизоване читання та редагування. Власник може видаляти, редактор змінює записи в межах своїх прав.
- `/api/admin/site-quick-settings`: публікація банера, посилань і частини перемикачів функцій через Railway, з перевіркою актуальної ревізії та прав.
- `admin-address.js`, `admin-address.css`: службова картотека точних адресних виправлень.
- `push-server/address-corrections.js`: адреса → підчерга; чернетка, підтвердження власником, публікація або відкликання.
- `/api/address-corrections`: лише опубліковані записи без внутрішніх приміток і логінів, призначені для локального накладання на офіційний індекс.
- Новий код включено до `scripts/build_pages.py`, CI та тестів. Поточні модулі адмінпанелі збережено.

**Статус розгортання 2026-10-21:** GitHub Actions staging успішні; Railway відхилив спробу оновлення із повідомленням `Deploys have been paused temporarily`. Доки бета API не оновлено і не перевірено з браузера, не можна казати, що нові API-функції працюють у встановленій бета-версії.

## 4. Важливий порядок обробки адрес

1. Офіційний перелік обленерго є базовим джерелом.
2. Архівні/географічні довідники допомагають **знайти назву**, але не можуть самостійно підтвердити підчергу.
3. Нові адресні уточнення створюються для **конкретного будинку**, не для цілої вулиці.
4. Для публікації необхідне посилання на офіційне джерело і **ручне підтвердження власника**. Посилання саме по собі не означає, що сайт машинно звірив цей будинок.
5. Після відкликання уточнення застосунок має повернутись до офіційного індексу на наступній синхронізації; в автономному режимі може бути останній збережений знімок.
6. Особистий вибір підчерги конкретним користувачем зберігається **лише для його адреси** і не змінює загальну базу.
7. Непідтверджену адресу не можна мовчки позначати як офіційно підтверджену. Для спірних відповідей зберігати статус перевірки та джерело.

## 5. Наступні модулі (в порядку пріоритету)

### P0 · Релізна надійність

- Розгорнути staging Railway, коли платформа дозволить деплоям знову працювати.
- Перевірити на живому API `/api/admin/work-items`, `/api/admin/site-quick-settings`, `/api/admin/address-corrections`, `/api/address-corrections`.
- Фактичний браузерний тест на iPhone і десктопі: логін, права, пошук, таби, редагування, чернетка → публікація → відкат.
- Перевірити оновлення SW/PWA, конфлікт змін двох адміністраторів і збереження після рестарту контейнера.
- Переконатися, що продакшн API, продакшн Volume і `main` не зачеплені.

### P1 · Єдина картотека і завдання

- Створення службового завдання з картки звернення в один клік.
- Зв'язування звернення, адресного уточнення, публікації та внутрішнього доручення.
- Коментарі по ходу виконання, вкладення з обмеженнями, службові примітки, відповідальні.
- Контроль строків: сьогодні, прострочені, очікують перевірки; віджети на робочому столі.
- Перегляд руху картки, повернення на доопрацювання та зміна виконавця.
- Фільтри й експорт реєстрів за датою, типом, відповідальним і статусом.

### P1 · Без GitHub

- Повне керування з адмінки посиланнями, користувацькими текстами, банерами, темами повідомлень, контактами та довідковими статтями через validated Railway state.
- Персоналізовані розсилки за підчергою та населеним пунктом (без вулиці та номера будинку в Push-базі).
- Підготовка й розклад публікацій, автоматичне завершення терміну їх показу, архівація.
- Повернення попередньої редакції без повторної Push-розсилки.
- Зміни глобального графіка лише за офіційним джерелом і підтвердженням, без вигаданих даних.

### P2 · Конструктори та автоматизації

- Службові шаблони карток і типових відповідей; шаблони маршрутів `нове → опрацювання → перевірка → виконано`.
- Набір безпечних автоматичних правил: нагадування про прострочені задачі, зняття банера після дати, групування повторюваних звернень.
- Чернетки змін за підсумками моніторингу. Автоматичний імпортер не має право самостійно підтверджувати неперевірену підчергу.
- Календар запланованих робіт, контент-план та операційний журнал за датами.
- Моніторинг джерел, Push, серверів, публікацій і синхронізації з видимими помилками.

### P2 · Аналітика та безпека

- Довільна початкова дата, довільний інтервал, останні 7/30 днів, порівняння періодів та експорт.
- Тільки агреговані метрики за добровільної згоди; без адрес, геолокацій або прихованого стеження за людьми.
- Ролі з правами на конкретні дії, журнал із редакціями, 2FA, захист від повторних запитів.
- Backup/restore з попереднім переглядом і явним підтвердженням; окремі staging і production сховища.
- Валідація всіх налаштувань на сервері, заборона довільного HTML/JS у конфігураціях.
- Чітка вказівка, які зміни оновлюються одразу, а які все ще потребують розгортання коду.

## 6. Безпечний процес розробки

1. Змінювати тільки `staging`, доки реліз не перевірено.
2. Зберігати робочі інструменти: повідомлення, Push, допомога, аналітика, звіти, графіки.
3. Додавати тести для кожного нового маршруту, статусу, ролі та сценарію відкату.
4. Не переміщати секрети в GitHub Pages. Backend-сховища на Railway, права лише через сервер.
5. Перед публікацією `main` робити огляд змін, smoke-тести та перевірку оновлення PWA.
6. Не змінювати версію основного застосунку або стан продакшну без окремого рішення.
