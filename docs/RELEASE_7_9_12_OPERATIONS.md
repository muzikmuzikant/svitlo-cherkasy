# Протокол випуску 7.9.12, 24 жовтня 2026

**Статус:** candidate in GitHub PR #77. Це не дозвіл на злиття у `main`, розгортання Production Railway чи сповіщення користувачів.

## Головне правило
- Повне Production оновлення **лише після прямої команди власника**. GitHub `main`, Production Railway `/data`, VAPID, API Origin, subscribers і реальні адреси не змінювати до команди.
- Beta (`staging`) має залишитися окремою PWA з власною підпискою; `main` зберігає власний `manifest.webmanifest` ID, `CNAME`, `push-config.json`, `robots.txt`.
- Релізна гілка містить `release.json` = 7.9.12 / production. Нові користувацькі зміни описуються без згадування внутрішніх серверів/адмінки.
- Перед merge знову порівняти `main` і кандидата: графіки та `data/` можуть змінитися від автоматичного importer-а. Актуальні перевірені дані Production важливіші за старі дані релізної гілки.

## Коли і які технічні роботи

**Зараз вимкнені. Не вмикати на етапі CI.**

Після команди «релізити»:
1. Якщо зміни стосуються тільки статичних сторінок і безпечного rolling backend-deploy без перерви у записі, технічні роботи **не потрібні**.
2. Якщо під час узгодженого Production backend deploy тимчасово не можна безпечно створювати звернення або змінювати Push-підписки, **перед фактичним деплоєм** через Production-адмінку поставити `maintenance.enabled=true`, `maintenance.mode='limited'`, `disabledModules=['feedback','push-settings']` лише для потрібних функцій. Не вимикати серверний Push-диспетчер або читання графіків.
3. Текст заголовка: «Оновлюємо застосунок». Текст пояснення: «Деякі функції можуть бути тимчасово недоступні. Графіки відключень залишаються доступними.»
4. Після здорового Production API, синхронізації графіків та перевірки запису звернень і Push-підписок поставити `maintenance.enabled=false`; перевірити з PWA.
5. `full` або `incident` лише за **справжньої критичної проблеми**, наприклад недостовірний live-графік чи неможливість безпечно користуватися всім PWA. Звичайний реліз не привід приховувати графіки.

Важливо: `limited` контролює елементи інтерфейсу, але не обов'язково є backend-бар'єром для всіх запитів. До активації переконатися, що сервер безпечно обробляє записи або зупинити лише відповідну операцію без вимкнення Push. Не призначати фальшивий ETA завершення.

## Після отримання окремого дозволу
1. Зафіксувати актуальний Production commit SHA, backup і статус робочої БД.
2. Визначити чи потрібний `limited`; проінструктувати власника **до** розгортання, якщо потрібен.
3. Контрольовано оновити лише код Production гілки від актуального `main`, зберегти перевірені `data/`, PWA identity, VAPID і `CNAME`. Виконати CI на тому SHA.
4. Безпечно оновити Production backend з тієї самої погодженої версії; не замінювати `/data`, VAPID та підписки.
5. Перевірити доступність графіків, логів, дублювання Push, адмінки, звернень та оновлення SW.
6. Вимкнути `limited`, якщо він був потрібен, і повідомити власника про завершення. При критичному збої зупинити подальші зміни, відкотити код, але **не** затирати нові живі дані.

Документ підготовлений для безпечного handoff; ніяких прихованих або автоматичних дій Production не робить.
