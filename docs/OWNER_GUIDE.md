# Світло Черкаси | Інструкція для власника без досвіду програмування

Це окрема проста пам'ятка, щоб наступний ШІ міг продовжити роботу навіть у новому чаті або без підписки ChatGPT Plus. **Усі основні технічні рішення описані в [AGENTS.md](../AGENTS.md) та [повному handoff](AI_HANDOFF_MASTER.md).** Цей файл спеціально написано людською мовою й розраховано на iPhone.

## 1. Як почати новий чат із будь-яким ШІ

Відкрий новий чат з асистентом, який уміє читати GitHub (через підключення GitHub, доступний інструмент, або якщо потрібно просто публічний URL). Встав цей короткий текст:

> Продовжуємо розробку PWA «Світло Черкаси». Репозиторій: https://github.com/muzikmuzikant/svitlo-cherkasy . Перед будь-якими змінами уважно прочитай файл AGENTS.md у гілці документації, потім усі документи docs/AI_*.md і docs/OWNER_GUIDE.md, DESIGN_RULES.md, SCHEDULE_DISPLAY_CONTRACT.md. Перевір поточний main, staging, PR, конфігурацію деплоїв і версії. Працюй спочатку в Beta, не чіпай Production без моєї прямої команди. Самостійно зроби код, тести, GitHub PR, а не тільки план. Якщо я вкажу баг, шукай першопричину і перевір усю систему. Повідом мені конкретні результати з посиланнями.

**Важливо:** поки документація ще у гілці `docs/ai-continuity-handoff-20261020` і PR не злитий, потрібно дати ШІ **посилання саме на цю гілку**, а не на старий `main`. Після схваленого merge у `main` звичайне посилання на репозиторій достатнє.

Приклад прямого посилання на головні інструкції у гілці документації:
`https://github.com/muzikmuzikant/svitlo-cherkasy/blob/docs/ai-continuity-handoff-20261020/AGENTS.md`

Якщо новий ШІ не має доступу змінювати GitHub, попроси готову зміну у вигляді patch/архіву і чіткі інструкції; але краще підключити GitHub, ніж вручну переносити сотні файлів.

## 3. Що таке `main`, `staging`, `PR`

- **main:** код, який може опинитися у всіх користувачів. Цю гілку не змінювати під час звичайних експериментів.
- **staging:** тестова версія з майбутніми функціями. Нові зміни потрібно спочатку робити тут, через окремі тимчасові гілки.
- **branch:** окрема копія історії змін, де розробник безпечно працює.
- **Pull Request (PR):** запит перенести зміни з однієї гілки в іншу. Сам по собі PR не означає, що зміни вже доступні всім.
- **merge:** прийняти зміни в цільову гілку. Якщо base = `main`, після merge може початися оновлення основного сайту.
- **deploy:** сайт або сервер реально оновився на хостингу. Новий commit і успішний PR самі по собі не доводять, що потрібна версія вже запущена.
- **CI/Checks:** автоматичні перевірки коду. Зелені тести корисні, але не заміняють перевірку iPhone.

**Висновок:** якщо ШІ пише «готово», спитай: «Де PR, в якій гілці, які тести пройшли і як перевірити в Beta?». Коли будеш задоволений, окремо скажи «випускай у Production» для конкретного оновлення.

## 4. Перевірити PR на iPhone

1. Відкрий Safari або GitHub App і перейди на репозиторій.
2. Торкнись вкладки **Pull requests**.
3. Відкрий потрібний PR, перевір назву і короткий опис.
4. Подивись **base** (куди має потрапити зміна) і **compare/head** (звідки беруть код). Для первинного тесту target має бути `staging`, для окремо узгодженого релізу `main`.
5. У вкладці **Files changed** видно, що саме змінювали.
6. У **Checks** переконайся, що немає очевидних помилок.
7. **НЕ натискай Merge**, якщо це Production-реліз, який ще не затверджував.

Якщо в мобільному GitHub не видно кнопки чи вкладки, відкрий сторінку у Safari і за потреби натисни **aA → Запитувати настільний вебсайт**, але у більшості випадків простіше попросити ШІ дати пряме посилання.

## 5. Як самому перевірити Beta

1. Відкрий **https://svitlo-cherkasy.pages.dev** на iPhone у Safari.
2. Якщо з'явився екран встановлення, скористайся **Поділитися → На початковий екран**. Користувацький PWA задуманий для встановлення.
3. Запусти Beta з іконки на головному екрані.
4. Обери тестову адресу та підчергу, перевір головну і графіки.
5. Переконайся, що на екрані все вміщується, немає дивного масштабування, некоректних іконок чи ривків.
6. Перевір наявність назв `Івана Кожедуба` (Черкаси) і `Філатова` (Слобода), якщо тестується адресний фікс; якщо нема, повідом ШІ **конкретний результат**, бо готовий PR не дорівнює оновленій Beta.
7. Відкрий повідомлення, подивись анімацію відкривання/закривання і меню дій.
8. Для тестування Push узгодь із ШІ **безпечний тест лише на свій пристрій у Beta**, не надсилай на всіх користувачів.

Не видаляй основний production PWA заради тесту бети. Різні вебадреси й PWA identities допомагають тримати їх окремо.

## 6. Як побачити, чи оновився GitHub Pages

1. На GitHub відкрий вкладку **Actions**.
2. Знайди workflow **Publish Svitlo Cherkasy PWA**.
3. Відкрий останній потрібний запуск.
4. Зелена галочка означає, що build/deployment pipeline спрацював; окремо перевір live сайт.
5. Відкрий `https://svitlo-cherkasy.pp.ua/release.json` і перевір версію. На дату цього документа Production мав `7.9.10`. Якщо дата пізніша, цифра цілком може бути іншою.
6. Якщо iPhone PWA показує стару версію, спочатку повністю закрий/відкрий застосунок і перевір зв'язок; не видаляй його без потреби. Попроси ШІ перевірити Service Worker і deployment.

Для Beta сайт оновлює Cloudflare Pages, там інші журнали deploy. Якщо асистент сам має інтеграції, попроси перевірити їх замість тебе.

## 7. Як передати новому ШІ проблему зрозуміло

Хороший приклад:

> В Beta на iPhone у встановленому PWA, вкладка «Адреси»: с. Слобода, вулиця Філатова відсутня у підказках. Перевір весь шлях: джерело назв, імпорт, JSON, app.js, address-lookup.js, Service Worker, активний beta deploy. Додай регресійний тест. Я не хочу вигаданого номера будинку чи підчерги. Виправ у Beta, покажи PR.

Інший приклад:

> У Production я видалив звернення в адмінці, але воно залишилося в користувача. Нічого не видаляй масово із серверної бази. Досліди синхронізацію server → client, tombstone, localStorage, cache та realtime. Виправ спочатку на Beta, з тестом після reload і без reload.

Ще один:

> Push про повернення приходить, а нагадування перед відключенням при закритому PWA ні. Досліди server event IDs, offsets, актуальність даних, VAPID і service worker. Не надсилай тестові масові Push. Дай перевірений результат.

Ключове: **назви Beta/Production, екран, фактичну поведінку та очікувану**. Навіть без технічних знань це допоможе ШІ не зробити фіктивне виправлення.

## 8. Як випускати оновлення без ризику

Найкращий сценарій:
1. Попроси: **«Роби на Beta, main не чіпай»**.
2. Перевір Beta на iPhone. Якщо не сподобалось, скажи, що саме: баг, анімація, текст, іконка.
3. Коли все добре: **«Підготуй окремий release PR з актуального main, перенеси тільки перевірені зміни, збережи всі production config, живі графіки, Push і рекламу вимкненою»**.
4. Переглянь підсумок, тести і список можливостей.
5. Якщо готовий: **«Випускай саме цей PR у Production»**.
6. Після виходу перевір сайт/встановлений PWA, реальний графік і Push.

Ніколи не передавай новому ШІ пароль від адмінки, особистий токен GitHub або приватний VAPID-ключ просто в повідомленні. Якщо він має право змінювати конфігурацію Railway, він повинен сказати, які змінні встановити через захищені settings.

## 9. Як підключити інструменти після закінчення Plus

Платний план може змінювати обсяг доступних можливостей, але **сам код GitHub, Beta і Production не зникають** через закінчення підписки ChatGPT. Доступ конкретного ШІ до GitHub/Railway залежить від того, які інтеграції та функції доступні у твоєму плані на момент роботи.

Якщо новий ШІ не бачить репозиторій:
1. Дай йому пряме посилання на публічний GitHub і `AGENTS.md` у гілці документації.
2. Запитай, чи може він переглядати публічні файли й готувати patch або PR через GitHub.
3. За наявності доступу до інтеграцій підключи потрібні інструменти у налаштуваннях програми; нікому не давай пароль.
4. Якщо він може лише читати, нехай підготує точно названі файли й diff/patch. Тоді виконуй мінімум ручних дій, а не десятки копіювань.
5. Зберігай ці документи в репозиторії як незалежну від платформи пам'ять про весь проєкт.

**Репозиторій публічний.** Зберігай у ньому лише технічні інструкції й несекретну інформацію.

## 10. Як зрозуміти, чи ШІ тобі справді допоміг

Гарний підсумок виглядає приблизно так:

> «Я знайшов, що під час імпорту губилася частина назв вулиць, а кеш не завжди оновлювався. У гілці fix/... змінив парсер, злиття каталогу та Service Worker, додав тест для двох адрес і тест після повторного імпорту. Усі локальні тести пройшли, PR: [посилання]. На Beta URL необхідно перевірити конкретний deployment; справжній iPhone ще не тестував, тому production реліз не схвалений.»

Поганий підсумок: «Я повністю пофіксив усе! Просто зайди перевірити», без PR, коду, тестів і статусу.

Твої вимоги достатньо серйозні для справжньої дисципліни розробки. **Вимагай доказів, а не обіцянок**.

## 11. Резервне копіювання й облікові записи

GitHub історія зберігає код, але **не замінює** резервну копію Railway persistent data, VAPID ключів, приватних звернень і підписників. Резервні копії потрібно робити лише безпечно, не розкривати їх у публічному репозиторії. Не видаляй Railway проєкт, volume або домен для «простого reset».

Важливо зберігати доступ до GitHub, Cloudflare Pages, Railway і домену. Паролі та recovery codes краще зберігати у власному захищеному менеджері паролів, а не у документації.
