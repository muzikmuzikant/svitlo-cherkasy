# Світло Черкаси | Реєстр проблем, QA, критерії готовності й релізні правила

**Знімок запитів станом на 20.10.2026.** Це не таблиця гарантовано відкритих GitHub issues і не автоматичний список поточних production-багів. Це реєстр того, що власник просив, що вже колись ламалося і що наступному ШІ **потрібно перевіряти**. Мітки нижче: `КОНТРАКТ` = правило продукту; `ІСТОРІЯ РЕГРЕСІЇ` = баг уже траплявся, навіть якщо зараз може бути виправлений; `НЕПІДТВЕРДЖЕНО` = поточний status треба перевірити на конкретній гілці й пристрої; `ОКРЕМИЙ РЕЛІЗ` = не вмикати самовільно.

## 2. Адреси: P0, довготривалий біль

**Скарга власника:** проблема від першого дня розробки, у багатьох населених пунктах немає до половини вулиць, а точкові «додали пару назв» не працюють. Конкретні приклади: `м. Черкаси, вул. Івана Кожедуба` і `с. Слобода, вул. Філатова`. Раніше назви Слободи теж губилися після імпортів.

**Тестова матриця:**
- реальна вулиця повертається у suggestions і допускає збереження **без** номера будинку;
- `Івана Кожедуба`, `Філатова` знаходяться у **правильному** населеному пункті, а не сусідньому;
- старе `Червона Слобода` мапиться на `Слобода`, але не створює подвійний пункт;
- тип `пров.` не плутається з `вул.`, неоднозначні однойменні вулиці не зливаються;
- `вул. А, Б, В` у PDF породжує всі три назви, а не тільки першу;
- псевдонаселені пункти з ініціалів `М.` не виникають;
- у разі street-only однозначної офіційної підчерги не вимагати house; у разі house split не вгадувати підчергу;
- OSM/GIS створює пошукові топоніми, але не автоматичну електричну чергу;
- fallback до офіційного ресурсу існує для невідомої адреси, не обіцяє неперевіреного prefill;
- повторний daily importer не стирає назви; public PWA отримує нову версію даних з урахуванням SW;
- створені/відредаговані звернення про відсутні адреси не пропадають у користувача при admin delete.

**Код і тести:** `scripts/update_data.py`, `data/addresses.json`, `address-lookup.js`, `data-merge.js`, `app.js`, `sw.js`, `tests/test_address_catalog_v793.py`, `tests/test_district_import.py`, `tests/test_address_lookup.cjs`, staging-PR від 20.10.2026. **Статус на поточному Beta перевірити, не вгадувати.**

## 3. Графіки: P0/P1, регресії

**ІСТОРІЯ РЕГРЕСІЇ:** після міграції cron на Railway застосунок писав «не вдалося отримати графіки». Виправлення вимагає відокремити publish fail, Railway snapshot, CORS, client fetch priority, SW stale response, помилкову локальну дату.

**ІСТОРІЯ РЕГРЕСІЇ:** після ручного оновлення графіка в GitHub зміну було видно лише після manual run; власник хотів наближене до real-time оновлення, обговорювали 1 хв замість 5 хв. `RAILWAY_SCHEDULES.md` описує Cron 5 хв, а окремий PR розробляв 60-секундний worker; **не вважати його активним без перевірки Railway**. При перевірці затримки розділяти час ПУБЛІКАЦІЇ джерела, час СКАНУ, час ПУБЛІКАЦІЇ snapshot, час PWA fetch і час Push.

**ІСТОРІЯ РЕГРЕСІЇ:** пропав понеділок/було вісім днів, зайві дати замість простих назв днів. На релізній гілці 7.9.12 готувались фіксовані 7 кнопок і логіка переходів. Прийняття: 7 кнопок Пн-Нд, в неділю і на межі тижня без неправильної навігації та втрати опублікованого майбутнього дня.

**КОНТРАКТ:** 24 зелені години і «Світло весь день», коли немає опублікованого графіка. **Не переписувати.** Контрольні тести: `tests/test_forecast_v711.mjs`, `tests/test_verified_absence_and_publication.mjs`.

**ІСТОРІЯ РЕГРЕСІЇ:** обернений півгодинний сегмент: 19:30-20:00 off помилково показувався як 19:00-19:30 off. Контроль `hour-paint.js`, `test_hour_paint.cjs`, `tests/test_hour_paint.cjs`.

## 4. Push та Inbox: P0/P1

**ІСТОРІЯ РЕГРЕСІЇ:** зміни видно у вкладці повідомлень, але немає нативного Push при закритому встановленому PWA. Інша проблема: надходить повернення світла, але відсутнє нагадування перед відключенням. Також були **два однакових Push** на одну подію.

**Приймання:** два ізольовані тестові підписники, закритий PWA, опублікований тестовий сценарій у Beta без реальних масових розсилок. Для потрібної підчерги та часу надходить одне відповідне повідомлення; event ID стабільний; Inbox не дублює; відповідні інші підчерги не отримують чужі нагадування; permission-off показує людяний CTA, а не crash. Фактичні обмеження iOS окремо описати.

**ІСТОРІЯ РЕГРЕСІЇ:** повідомлення, яке видалили чи зняли з публікації в адмінці, залишалось у користувача до перезапуску або поверталось з кешу. Тестувати authoritative snapshot, stale IndexedDB, SW push, tombstones, resubscribe/reconnect і два пристрої.

**КОНТРАКТ UX:** повноекранне повідомлення плавно відкривається **і закривається**; меню дій плавне в обидва боки; share надсилає посилання на конкретний запис; жодних «квадратів» замість іконок. Не ставити статичний скріншот як доказ динамічної анімації.

## 5. Звернення: P1, наскрізний стан

**ІСТОРІЯ РЕГРЕСІЇ:** видалене в адмінці звернення залишалось у користувацькому списку. **Запит:** повна перебудова user+admin workflows, realtime, красивий UI, анімації.

Матриця:
- створення/валидація форми і додаткових полів;
- помилки запиту, повторний submit без дублювання;
- коректний статус `new/in_progress/resolved`, текст відповіді;
- приватний token, відсутність можливості читати чужу заявку за ID;
- швидке оновлення відкритої користувацької сторінки з другого пристрою;
- видалення -> server tombstone/404/410 і очищення власного local card;
- server reconnect/polling backup, тривалі запити не блокують навігацію;
- фокус, клавіатура iOS, кнопка «назад», анімовані деталі;
- видимість повідомлення, без секретів у логах.

Приватність і retention перевіряти фактично, не підганяти політику під припущення.

## 6. Адмінка: P1, повне QA

**ІСТОРІЯ РЕГРЕСІЇ:** елементи перекриваються на desktop, різні settings pages відображаються криво, зміна pinned/published не відбивається в клієнта до restart, редагування/видалення запису поводиться непослідовно, адміну потрібно повторно логінитися.

Перевір:
- secure admin login (server validation, сесії, CORS із правильного origin), logout, неправильний пароль, прострочений token;
- широка desktop верстка + iPhone mobile, контрасти, відсутність overflow;
- публікація/зняття/видалення/закріплення кожного message, server revision, списки;
- maintenance, important banner, emergency flag, допомога, редактор великих текстів і медіа;
- feature flags відображаються й діють після reload;
- експорт/пошук звернень, категорії, status, відповіді;
- правильний `lastChecked` джерела: не плутати час HTTP-запиту, час останнього успішного імпорту, час офіційної публікації;
- необов'язкова аналітика працює після згоди й не називає «активних людей» за кількістю відкриттів;
- рекламний центр не відкриває Production покази.

## 7. Дизайн, iOS, анімації: P1/P2

**ІСТОРІЯ РЕГРЕСІЇ:** горизонтальна прокрутка/масштабування iPhone, double-tap zoom на кнопках днів, вкладки із «телепортом» у фінальному кадрі, анімації лише на opening, відсутність анімації action menu, поламані іконки-квадрати.

Мінімальні реальні перевірки:
- iPhone Safari на сторінці встановлення і відкритий installed PWA;
- ширина різних iPhone viewport, safe-area top/bottom, клавіатура, scroll lock;
- швидке перемикання вкладок 1→2→3, повторний тап поточної вкладки, 20 швидких тапів;
- різна висота контенту попереднього/наступного екрану, scroll знизу, розрив анімації;
- входи/виходи з full-screen detail, меню, FAQ, modal, preview;
- `prefers-reduced-motion`, VoiceOver/focus, Escape/back navigation;
- no horizontal overflow на будь-якій вкладці й в адмінці;
- зміна версії SW у встановленому PWA, без вічного splash;
- офлайн повторний запуск на збереженому кеші або зрозумілий fallback з кнопкою повтору. Історична скарга: без інтернету застосунок взагалі не завантажувався. Не приписуй «offline готово» тільки через реєстрацію SW.

**Неприйнятно:** замінити гарні оригінальні іконки на `ϟ`, `◇`, `▤` тощо, декоративні текстові символи чи масове емодзі; знищити анімацію вкладок; додати затримку перемикання. Докладніше: `DESIGN_RULES.md`.

## 8. Версії, оновлення, релізний банер

**Раніше:** головний `main` і Beta суттєво відрізнялися; навіть коли функція перевірена в Beta, її могли **забути включити у production release**. Регресії: анімація закриття повідомлень і частина попереджень/announcements.

**Приймання:** порівняй release candidate із функціональним чеклистом конкретної Beta; вимоги, які ввійшли до нової версії, мають бути присутні в коді main-based candidate, а не лише у staging. Збережи production-only дані й конфіг. Зміна `release.json` синхронізується з `build_pages.py`, `sw.js`, PWA update flow; сайт і встановлений PWA повинні мати однакову узгоджену версію.

**Заборонено в банері:** технічні слова «зміни на бекенді», «налаштували Railway», «оновлено API», «нова адмінка», якщо це не функція для користувача. Якщо лише виправлення: **«Виправлення помилок».**

## 9. Комерція, підтримка та аналітика: ОКРЕМИЙ РЕЛІЗ

Майбутня модель реклами продумувалась як централізовано керована, тарифні плани, гнучкі поля контактів і оплата, пріоритети/частки показів кампаній. Власник прямо обмежив показ **ЛИШЕ головною сторінкою**. До окремого релізного дозволу **Production рекламний API повинен fail-closed**, не показувати кампанії або приватні контакти/оплату.

Не вимикати `Підтримати проєкт` просто через те, що вимкнена комерційна реклама; це була окрема виправлена регресія. Чинні правові тексти, платіжні реквізити й аналітика можуть вимагати перевірки; автор проєкту керує цими рішеннями.

Аналітика реальних інсталяцій: рахувати добровільно дозволені **інсталяції**, не приписувати відкриття конкретним людям. Користувач без згоди не враховується; мала група населеного пункту не видається за анонімну без перевірки.

## 10. Матриця релізного приймання

| Категорія | Обов'язковий контроль |
|---|---|
| Git / pipeline | PR у правильну base branch, clean diff, без `/data` і секретів, tests green, збережено main-only data |
| Сайт | правильний `release.json`, SW version, існуючі іконки, install gate, manifest ID, SSL/domain |
| Графіки | сьогодні/завтра/7 днів, неділя/понеділок, 19:30, відсутній день, свіжий Railway snapshot |
| Адреси | Філатова, Івана Кожедуба, села, no-house street, house split, no fake queue, cache refresh |
| Push | installed iPhone, 30/15 хв сценарії, закрите PWA, no duplicates, Inbox |
| Realtime | зміни повідомлень і звернень видно на двох пристроях без reload, reconnect/fallback |
| Візуально | iPhone no zoom/scroll, all transitions both directions, відсутні квадрати і технічні написи |
| Адмінка | login/CORS, CRUD, публікація/видалення, desktop і mobile, feature flags |
| Права/безпечність | consent, мінімізація даних, privacy/terms, no mass Push, реклама off |
| Release | власник дав явне «випускай» саме для цієї версії, перевірено production після merge |

**Автотести != фізична перевірка iPhone.** Якщо реального девайса не було, залиште відповідний тест у статусі «не перевірено вручну».

## 11. Формат передачі стану після кожної зміни

Приклад запису у PR / issue / технічному handoff:

```markdown
### Що просив власник
[коротка точна цитата потреби]

### Фактична проблема і причина
[знайдений шлях даних і race/cache/parser/API причина]

### Реалізація
[файли, архітектурні рішення, межі змін]

### Гілка, commit, PR
[точні URL, base/head]

### Перевірки
- PASS: [команда і суть]
- НЕ ПЕРЕВІРЕНО: [реальний iPhone, Railway, тощо]

### Ризики
[що може зламатися, відкат]

### Статус
Beta ready / Needs review / Owner-approved release / Production live
```

Статуси не можна змішувати. `Beta ready` не означає `Production live`. Зробити користувацький текст релізу до того, як код опубліковано, не означає виконати реліз.

## 12. Оновлення цього backlog

Коли власник підтверджує нову вимогу, записуй її з датою, контекстом, точним критерієм приймання та де змінено код. Не «закривай проблему» словами. Додай тест, потім після дійсного релізу познач фактичний Production commit. Якщо є протиріччя між вимогами, пріоритет має найновіша явна інструкція власника; зафіксуй її без стирання історії.
