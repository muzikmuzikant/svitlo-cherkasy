# PUSH надійність: Beta 7.9.12, 24 жовтня 2026

## Межі змін

Тільки гілка `staging`, сервер `svitlo-beta-api` Railway і Beta PWA. Production не змінювати без дозволу власника.

## Що виправлено

1. Окремо фіксується факт прийняття повідомлення Web Push-провайдером та факт успішного виклику `showNotification()` у service worker. Друге не означає прочитання, ані абсолютної гарантії показу на пристрої.
2. Для кожного автоматичного PUSH сервер створює випадковий 24-символьний `receiptId`. У файловому сховищі на постійному Railway volume містяться лише стан, дата, категорія, підчерга. Адреса, IP, браузерний endpoint та персональні дані до журналу не потрапляють.
3. Service worker насамперед викликає системне `showNotification()`; якщо багатий варіант із іконками не працює, пробує мінімальне сповіщення без необовʼязкових опцій.
4. Після успішного виклику service worker робить best-effort POST `/api/push/receipt`. При збої мережі показ і запис у «Вхідні» не блокуються. Підтвердження перевіряється випадковим токеном, строк його дії 48 годин.
5. Довгі ідентифікатори повідомлень отримують унікальний стабільний `tag`; нова ревізія графіка не повинна замінити інше, несхоже повідомлення.
6. PWA не генерує друге системне сповіщення при поверненні у застосунок, якщо згоду на серверні PUSH вже було надано або їх вимкнули. Локальна вкладка «Вхідні» все одно може зберігати записи без надсилання нового системного PUSH.
7. Перевірка підписки охоплює всі пʼять налаштувань: off, on, changes, tomorrow, emergency.
8. У вкладці «Push-розсилки» в адмінці показуються агреговані лічильники прийнятих повідомлень та підтверджень service worker.

## Перевірка

CI: `Push Delivery Regression Checks` має запускатись на кожен push до `staging`. Виконуються синтаксичні перевірки та тести `tests/test_push_receipts_beta.mjs`, `tests/test_transition_server_dispatch.mjs`, `tests/test_push_delivery_health.mjs` та інші.

Після деплою перевірити:
- Railway `svitlo-cherkasy-beta / staging / svitlo-beta-api` на найновішому SHA staging, без збоїв запуску.
- GET `/health`: поля `delivery` та `browserDisplay`, наявність актуального графіка.
- Адмінка: облікові записи й доступи, показ числа підписок і лічильників за 48 год.
- Реальний iPhone (встановлена Beta PWA з домашнього екрана) та Android (встановлена PWA): увімкнути PUSH, перевірити всі 5 перемикачів, закрити застосунок, дочекатись **справжньої** запланованої події. Ніяких масових тестових PUSH без окремої згоди.
- Перевірити OS-дозволи на сповіщення, режими «Фокусування/Не турбувати», роботу при заблокованому екрані, а також повернення після короткої втрати мережі.
- Для 404/410 провайдера потрібне повторне оформлення підписки користувачем після повернення в PWA. Неможливо примусово доставити PUSH на відкликаний браузером endpoint.

## Важливі обмеження

- Відповідь Web Push-провайдера з успіхом не гарантує показу. Навіть `showNotification()` не гарантує, що користувач побачив або прочитав повідомлення.
- Клієнт може не відправити receipt через закінчення часу життя service worker або офлайн. У такому випадку число «без підтвердження» не є тотожним числу реально втрачених PUSH.
- Не відновлювати нагадування, коли час відключення/відновлення вже настав; та не надсилати їх за непідтвердженим або застарілим графіком.
- Зберігати `DATA_FILE`, VAPID і volume, не переносити конфігурацію Beta до Production.
- Для абсолютної перевірки потрібні реальні пристрої: тести Node.js перевіряють контракти, а не iOS/Android OS delivery.

## Попередня проблема з Railway

На момент перевірки в Beta API був застарілий деплой від 23 жовтня, попри нові коміти staging. Відновлено підключення джерела до гілки staging, після чого Railway запустив збірку оновленого Beta API. Перевіряти SHA кожного наступного деплою.
