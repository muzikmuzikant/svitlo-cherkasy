# Світло Черкаси: staging 7.9.12, перевірка вкладень і юридичних текстів

**Статус:** зміни лише у гілці `staging`. Реліз `main` залишається 7.9.11. Не переносити в `main` без окремого підтвердження власника.

## Що реалізовано
- Фото JPG, PNG, WebP, HEIC/HEIF до 4 МБ; короткі відео MP4, MOV, WebM до 8 МБ.
- У одному повідомленні максимум три вкладення, до 9 МБ разом.
- Сервер читає максимум 13 МБ JSON на звернення або повідомлення; обмежує кількість звернень і окремо частоту завантаження приватних вкладень.
- Бінарні файли живуть лише в `<directory-of-FEEDBACK_FILE>/ticket-media` на приватному сховищі Railway, метадані в приватному файлі звернень. Публічна `/api/media` не має доступу до цих файлів.
- Перегляд користувачу: лише за номером і приватним токеном звернення. Перегляд оператору: авторизований `/api/admin/feedback/attachment/<ticket>/<file>`; без відкритої URL.
- Видалення звернення та очищення звернень після 90 днів видаляє пов'язані бінарні файли.
- Підтримка вкладень рекламується API `/api/feedback/categories` у `capabilities.attachments`; UI приховує завантаження, доки сервер не підтвердить підтримку. Відповідь на надсилання також підтверджує кількість прийнятих файлів.
- `privacy.html`, `terms.html`, `help.html`, `about.html` і форма підтримки містять пояснення про вкладення, приватність, термін зберігання та зовнішні соцмережі.
- Версія `release.json`, `index.html`, `feedback.html` і `sw.js`: **7.9.12 beta**.

## Ручні сценарії перед релізом (обов'язково)
1. На iPhone вибрати 1 JPG і 1 HEIC; перевірити прев'ю, прибирання одного файла та успішне надсилання.
2. Вибрати MOV (до 8 МБ) й отримати підтвердження; на Windows/Chrome оператор перевіряє відеоплеєр і захищене завантаження оригіналу за відсутності кодека.
3. Надіслати файл із першого звернення та окреме повідомлення лише з вкладенням. Нові повідомлення мають з'являтися автоматично без перезавантаження.
4. Відкрити чужий attachment ID зі своїм токеном; має бути 404. Спробувати доступ без токена; має бути 403. Доступ без адмін-сеансу за адміністративним URL також відхиляється.
5. Спробувати HTML, SVG, фальшивий MIME та файли більші за ліміт; сервер відхиляє, файловий каталог не поповнюється.
6. Видалити звернення в адмінці. Переконатися, що воно зникло у користувача, а бінарні файли прибрано.
7. Перевірити темну й світлу тему, зменшення руху, iPhone viewport, клавіатуру, прокручування, прев'ю фото та відео.
8. Перевірити бета-сервер Railway: після оновлення API відповідає `capabilities.attachments: true`. Якщо ні, інтерфейс не показує кнопку додавання файлів.
9. Перевірити реальний деплой **обох** компонентів staging (Frontend GitHub Pages/Pages та Railway staging) та пробне завантаження невеликого файла. Самої перевірки коду недостатньо.
10. Перевірити повноту `privacy.html` і `terms.html` для конкретного власника сервісу.

## Юридичні відкриті питання
- Потрібно остаточно визначити та **опублікувати дані володільця персональних даних і сталий офіційний контакт**. Наразі сторінки прямо позначають це як неузгоджене. Не вигадувати ім'я, адресу або юридичний статус.
- Перевірити фактичне розміщення даних Railway, субпідрядників, можливі резервні копії й строки їхнього зберігання; не обіцяти миттєвого видалення з резервних копій без підтвердження.
- З'ясувати, хто й на якій правовій підставі опрацьовує вкладення, що можуть містити персональні дані інших осіб; оцінити обов'язки за Законом України «Про захист персональних даних» (статті 6, 8, 12).
- Якщо для масового релізу потрібні додаткові організаційні заходи чи особлива процедура прийняття умов, це має підтвердити компетентний юрист, а не сам застосунок.
- Переконатися, що бета-версія не переноситься у `main` без прямої команди власника.
