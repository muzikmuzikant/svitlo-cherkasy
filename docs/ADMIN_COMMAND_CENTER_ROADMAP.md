# Світло Черкаси: план розвитку центру керування без коду

Дата: 21.10.2026  
Статус: технічний план. Не всі описані модулі реалізовано.

## 1. Мета

Адміністратор керує роботою сервісу через зрозумілі форми, не відкриває JSON, базу даних, Railway Variables або код GitHub для щоденних операцій.

Винятки: зміна програмної логіки, нові інтеграції, секретні ключі, інфраструктурні міграції і критичні налаштування безпеки. Їх не можна безпечно зробити довільними перемикачами публічної вебпанелі.

## 2. Правила розробки

- Жодних фальшивих перемикачів. Якщо функція відключається, її має реально перевіряти код клієнта і сервера.
- Усе, що адміністратор змінює, валідовано на сервері. Клієнтська перевірка лише для зручності.
- У будь-якої важливої дії є підготовка, попередній перегляд, чітке підтвердження, журнал, можливість відкату.
- Ніколи не переписувати всю конфігурацію зі старого стану без перевірки ревізії (ETag / updatedAt / SHA).
- Редактори не отримують прав власника; фінансові та безпекові операції тільки для власника.
- Аварійне повідомлення та підчергу не підтверджувати без офіційного джерела.
- Користувачу не показувати технічні назви серверів, JSON, внутрішніх джоб або ключів.
- Для iPhone: адаптивність, відсутність горизонтального скролу, плавні й доречні анімації, зрозумілий стан кожної кнопки.
- Дійсні дані не замінювати вигаданими або нулями у разі пропуску.
- Тексти українською, коротко, без надлишкових системних пояснень для звичайних користувачів.

## 3. Що в адміністрації вже є

Знайдено розділи: Огляд, Аналітика, Діагностика, Повідомлення, Push, Медіатека, Реклама, Звернення, Допомога, Функції, Оформлення, Техроботи, Джерела, Планувальник, Швидкі інструменти, Редактор даних, Доступ і права, Резервні копії, Історія версій, Журнал.

Наявна система вміє змінювати частину контенту, оформлення, прапорців функцій та повідомлень через Railway. Деякі операції досі спираються на GitHub JSON. При будь-якому розширенні перевіряти, чи можливість уже реалізована. Не дублювати модулі.

## 4. Аналітика

### Реалізовано в поточній гілці розробки

- Збережено швидкі фільтри 48 годин, 7 днів, 30 днів.
- Додано 90, 365 днів, від дати до сьогодні, власний проміжок, весь збережений період.
- Сервер розуміє дати включно, у календарі Europe/Kyiv.
- Старі погодинні події після 45 днів переносимо в анонімні денні підсумки; до трьох років.
- Денний графік переходить на тижневу або місячну деталізацію для довгих проміжків.
- Порівняння з аналогічним попереднім періодом лише коли є достовірне покриття.
- CSV без ID пристроїв, адрес або приватних ідентифікаторів.
- Не підміняємо події підрахунком людей.
- Для довільного минулого періоду не відтворюємо історичну унікальну аудиторію PWA з останнього стану інсталяцій.
- Реклама має окрему історію до 90 днів, а день визначається UTC: адміністратор бачить пояснення.

### Наступні задачі

1. Історія роботи імпортера: кількість успішних і неуспішних перевірок за день, затримка появи нового графіка, кількість корекцій.
2. Продуктивність: лише агреговані помилки JS, успішність завантаження розділів, кешовані/офлайн відкриття.
3. Push: кількість підписок, успішних спроб надсилання, недійсних підписок, без поіменного відстеження читання.
4. Анонімні події продукту: відкриття графіків, пошук адрес, поділення, робота зі сповіщеннями. Обмежена кількість подій, без адрес і точних маршрутів користувача.
5. Воронка онбордингу без обіцянки, що одна подія дорівнює людині.
6. Аналіз релізів: частка активних версій за згодою, частота помилок після релізу.
7. Порівняння двох довільних періодів, повний CSV із чіткими метаданими про покриття.
8. Щоденний анонімний звіт: агреговані KPI, попередження про аномалії; сповіщення адміну лише за суттєвих відхилень.
9. Налаштування видимих віджетів аналітики та порядку карток без зміни способу збору даних.
10. Окрема вкладка «Методологія»: які події рахуються, як обмежується приватність, з якої дати доступний кожен лічильник.

## 5. Модулі керування без редагування файлів

| Модуль | Форма | Серверна умова |
| --- | --- | --- |
| Адреси | Пошук, нова назва, стара назва, офіційна підчерга, будинки, джерело, статус підтвердження | Немає черги без перевірки; неоднозначність не маскувати |
| Підчерги | Затвердження, уточнення, масова перевірка і список конфліктів | Відкат, попередній перегляд, автор джерела |
| Графіки | Конструктор півгодинних інтервалів, запланована публікація, скасування | Не перетворювати відсутність даних на вигаданий графік |
| Офіційні джерела | URL, пріоритет, час перевірки, журнал помилок, режим резервного джерела | Тільки allowlist доменів, захист від SSRF |
| Імпортер | Пауза/відновлення, одна ручна перевірка, політика повтору, пояснення причини | Не дозволяти адміну запускати довільні URL або shell-команди |
| Push | Канали, шаблони, нагадування, час до події, тест, дедуплікація | Серверні обмеження, одна подія = один унікальний ключ |
| Повідомлення | Чернетки, відкладені публікації, закріплення, сторінка, зображення, архів | Санітизація тексту, перевірка прав |
| Технічні роботи | Початок, завершення, банер, винятки для адмінки, скасування | Fail-safe, авто-відновлення, журнал |
| Клієнтські функції | Прапорці з пошуком та описом впливу | Кожен прапорець дійсно працює у PWA |
| Дизайн | Колір, щільність, тексти, картки, порядок, попередній перегляд | Без довільного CSS/JS і небезпечного HTML |
| Реклама | Кампанії, частки показів, частотні ліміти, ціни, розклад, CTR | Релізний блок реклами не обходити панеллю |
| Підтримка | Контакти, публічні способи підтримки, цілі, матеріали | Валідовані безпечні посилання |
| Звернення | Категорії, шаблони, призначення, статуси, приватні нотатки | Мінімум персональних даних і доступ за роллю |
| Довідка | Статті, FAQ, контакти, пошук, історія редакцій | Чернетки й перегляд до публікації |
| Релізи | Версія, список змін для користувачів, банер оновлення | Жодних технічних деталей у публічному банері |
| Команда | Ролі, доступ, активні сеанси, запрошення, блокування | MFA, аудит, відкликання сеансів |
| Діагностика | Тести імпорту, Push, API, кешу, версій, залежностей | Лише allowlist безпечних тестів |
| Резервні копії | Автоматичні знімки, перевірка, порівняння, безпечний відкат | Шифрування, обмежений термін, перевірка власника |

## 6. Один універсальний процес зміни

1. Вибір сутності через пошук у панелі, наприклад «вулиця Соборна».
2. Показ поточного стану й джерела даних.
3. Форма зміни з прикладами та підказками.
4. «Перевірити»: schema, бізнес-правила, джерело, конфлікти, вплив на користувачів.
5. «Попередній перегляд»: точний diff, які екрани зміняться, кому підуть Push.
6. «Опублікувати»: повторна перевірка актуальної ревізії.
7. «Журнал»: хто, що, коли змінив, стара й нова версія, посилання на джерело.
8. «Скасувати»: контрольований відкат без повторної масової Push-розсилки.

Не зберігати в історії паролі, токени, точні адреси користувачів чи приватні поля звернень.

## 7. Дані та надійність

- Єдиний серверний реєстр керованих параметрів: назва, тип, межі, дефолт, рівень ризику, потрібна роль, спосіб застосування.
- Параметри, які не мають коду застосування, не показувати як активні перемикачі.
- Публікація зміни атомарна: транзакція або optimistic locking.
- Для критичних змін окремий режим підтвердження та попередній перегляд.
- Публічна PWA отримує лише дозволені параметри. Адмінконфіг, токени й приватні дані не потрапляють у JSON GitHub Pages.
- Адмін API: авторизація, заборона CORS з чужих origin, rate limits, аудит, жорсткі ліміти розміру запитів.
- Контент із редакторів не є довільним JavaScript/HTML, посилання перевіряються.
- Автоматичні резервні копії сервера й бази з перевіркою відновлення.
- Мінімізувати зміну production: pull request, автоматичні тести, резервна копія, поетапна публікація.
- Немає історичних даних: явно показуємо «немає даних», а не 0.
- Агрегація для приватності: малі групи приховувати, ID не включати до експорту.
- Наступний етап: окрема серверна база для конфігів і журналу (можлива SQLite на volume / PostgreSQL), міграції зі старого формату без втрати даних.
- Публічні графіки можуть бути статичними файлами, але джерело управління має бути структурованим і авторизованим.

## 8. Ролі

- Власник: повний доступ у межах дозволених команд, резервні копії, ролі, публікація важливих змін.
- Редактор: контент, чернетки, довідка, повідомлення без масової Push-розсилки, якщо не надано окремий дозвіл.
- Оператор: перегляд моніторингу, дозволені звернення та неоперативні дії.
- Перегляд: тільки читання дозволених агрегатів.
- Для кожного нового endpoint необхідний окремий permission, а не автоматичне право «settings».

## 9. Послідовність наступної реалізації

**P0.** Запустити і протестувати фільтр дат; додати guided publish без JSON; протокол покриття статистики; базові тести на DST, міграцію й відкат; виправити головні вузькі місця адмінки.

**P1.** Реєстр адрес і джерел, підтвердження підчерг, картки конфліктів, масовий імпорт з dry-run. Саме це найважливіше для точності графіків.

**P2.** Живий центр стану джерел/імпортера з безпечними командами, власні настроювані Push-шаблони й часові правила, метрики затримки оновлень.

**P3.** Єдиний реєстр налаштувань, нові поля CMS, реклама, підтримка, керування домашньою сторінкою, шаблони публічних сторінок.

**P4.** Повний журнал ревізій для всіх сутностей, резервні копії, діагностика, рольові права для командних операцій, автоматичні звіти.

**P5.** Пошукова панель «Що ви хочете змінити?» з переходом безпосередньо до відповідної форми, а не до файла або таблиці.

## 10. Критерії готовності

- Усі звичайні щоденні дії виконуються з вебадмінки.
- Зміни не губляться через інший відкритий браузер чи паралельного адміністратора.
- У режимі без GitHub admin не обіцяє публікації, якої не може виконати.
- Є тести мінімум на позитивний сценарій, конфлікт ревізій, некоректне джерело, відсутні дані, відкат.
- Поведінка PWA після перемикання опцій перевірена на iPhone Safari.
- Інформація про підчергу тільки підтверджена чи чесно позначена неоднозначною.
- Розширення аналітики не створює прихованих профілів користувачів.
