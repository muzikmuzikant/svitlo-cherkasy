## Підтверджена логічна помилка та виправлення
У початковому коді `app.js`, якщо для дня **немає опублікованого графіка**, викликався `new Int8Array(1440)` (24 години світла) навіть тоді, коли час перевірки джерела застарів, дата очікувала уточнення або оператор просто був недоступний. Крім того, Home та «Завтра» могли показувати «Світло весь день» незалежно від реальної свіжості джерела. Це особливо критично під час нестабільної роботи Railway.

Виправлення `verifiedNoSchedule(date)` розрізняє два випадки:
1. Оператор щойно перевірений, дата явно в `confirmedNoScheduleDates` (у старій схемі лише поточний/наступний день), немає неусуненої перевірки й зв'язок працює: **«Світло весь день»** без планових відключень.
2. Офлайн, старий `lastChecked`, `unresolvedDates`, відсутність підтвердження: **«Немає підтверджених даних»**. Не видавати відсутність прогнозу за підтверджену наявність електроенергії.

Оновлено `tests/test_verified_absence_and_publication.mjs`, `tests/test_release_fixes_7912.mjs`, додано `tests/test_verified_no_schedule_freshness.mjs`. Перед випуском перевірити все в повному CI та на фізичному телефоні.

## Що ця перевірка НЕ доводить
- Немає доступу до авторизованого Railway, тому не перевірено живу історію Push delivery, новий Beta backend, приватні API адмінки, збереження доручень/звернень, інтеграцію прикріплених матеріалів.
- Немає фізичного iPhone/Android; Chromium emulation не відтворює всі обмеження iOS Safari/WebKit, push background, keyboard, PWA update й системні дозволи.
- Відсутні автоматичні pixel-diff/скриншотні еталони для кожної внутрішньої модалки; частина естетичних нюансів і анімацій потребує ручної перевірки.
- «Всі кнопки перевірені» стверджувати не можна: тестують конкретні сценарії і контракти, включно з основними вкладками та сторінками, але не кожну комбінацію станів, реклами й відповіді API.
- Немає достатніх доказів актуальності ВСІХ черг/адрес Черкасиобленерго. Тільки офіційні файли й живі операторські дані дають це підтвердження.

## Практичний порядок після відновлення Railway
1. Звірити `staging` server commit/health/version з `staging` front commit.
2. Пройти сповіщення OFF/ON на реальному закритому PWA за тестовою підпискою й збереженим отриманням лише 1×.
3. Відкрити кожну роль адмінки та перевірити справжній API: звернення, публікації, доручення, медіа, соціальні посилання, техроботи й налаштування.
4. Протестувати не лише зелені тести, а й реальні графіки для поточної дати та адреси Слобода/Черкаси, 00/30-хвилинні межі.
5. Тільки після цього приймати рішення про production. **Не зливати `staging` у `main` напряму**.
