# Railway Cron · автоматична перевірка графіків

Окремий сервіс `svitlo-schedules-cron` у Railway запускає перевірку кожні 5 хвилин за UTC-розкладом `*/5 * * * *`. Використовує **той самий офіційний імпортер** `scripts/update_data.py`, що й попередній GitHub Actions.

## Стан першого розгортання

Для безпечного перенесення сервіс спочатку запускається зі змінною **`IMPORTER_ACTIVE=0`**. В такому режимі Cron виконується і завершується успішно, **нічого не публікуючи**. Старе автоматичне оновлення GitHub Actions залишається ввімкненим.

Для публікації через GitHub потрібен **fine-grained personal access token** з доступом тільки до `muzikmuzikant/svitlo-cherkasy` та дозволом **Contents: Read and write**. Токен вводиться **лише у Variables сервісу в Railway**, ніколи не в код/чат/публічний файл.

| Variable | Value |
| --- | --- |
| `GITHUB_REPOSITORY` | `muzikmuzikant/svitlo-cherkasy` |
| `GITHUB_BRANCH` | `main` |
| `IMPORTER_ACTIVE` | `0` до першої перевірки |
| `GITHUB_TOKEN` | секретний токен, у Railway Variables |

## Перемикання без втрати оновлень

1. Перевірити GitHub Actions: старий `update.yml` продовжує працювати.
2. Перевірити Docker збірку нового сервісу, коректний Cron та успішні записи `STANDBY`.
3. У Railway додати `GITHUB_TOKEN` з дозволом Contents: Read and write, тільки для цього репозиторію.
4. Встановити `IMPORTER_ACTIVE=1`.
5. Перевірити **справжній** запуск: журнал `PUBLISHED` або `OK — no schedule revisions`, а також `lastChecked` у GitHub. За потреби дочекатися публікації змін через звичайний GitHub Pages push.
6. **Тільки після цього** прибрати `schedule` з `.github/workflows/update.yml`. Залишити `workflow_dispatch` для аварійного ручного запуску.
7. У разі збою повернути GitHub cron (розклад `2-57/5 * * * *`) та встановити `IMPORTER_ACTIVE=0`, щоб не було двох одночасних імпортерів.

Два інші процеси GitHub Actions, імпорт адрес та екстрених подій, поки не переносимо.

## Технічні обмеження

- Railway Cron працює за UTC і може запускатися із затримкою, тому не гарантує точну хвилину.
- Якщо попередній запуск досі активний, Railway пропускає наступний.
- Публікація відбувається **одним атомарним комітом** двох JSON-файлів, без force-push; конфлікт спричиняє повторне читання.
- Реальні зміни публікуються відразу, перевірка без змін оновлює heartbeat лише приблизно раз на 30 хвилин.
- Скрипт обмежений у часі 240 секундами.
- Немає потреби надавати Railway доступ до Push-підписок або секретів VAPID.
