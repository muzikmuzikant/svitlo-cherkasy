# Доповнення v6.6 · Автоматичні Push та стійкість

- `PORT` і `DATA_FILE` у Railway **не змінюйте**, якщо сервер уже працює.
- Додано `schedule-engine.js`: прозорий розрахунок переходів між відключеннями, невідомі години ніколи не вважаються відомими.
- Автоматична відправка: до 12 паралельних сповіщень, без перекриття циклів; затримка таймера до 4 хв допускається без пропуску нагадування.
- Скасування екстрених обмежень може надсилати окреме повідомлення **лише після офіційної свіжої публікації**.
- `/api/unsubscribe` дає змогу власнику браузерної Push-підписки видалити запис із сервера. Нове налаштування у PWA керує згодою, щоб застосунок не перепідписував користувача після відписки.
- `/health` показує `lastPushCheck` і `pushCheckError` для перевірки успіху опитування. `ok:true` означає лише, що Node-сервер відповідає, а не гарантує коректність або своєчасність джерел.
- Планові дані й повідомлення про надзвичайні відключення завантажуються незалежно, тому помилка планового JSON не блокує перевірку аварійних повідомлень.
- Для v6.6 на GitHub Pages треба вибрати режим **GitHub Actions**. Покроково — `ПОЧНИ_ТУТ.txt` у корені.

# v6.5 · Вхід до адмінпанелі за паролем

Оновіть `push-server/admin.js` і `push-server/server.js` із ZIP у GitHub та перевірте новий Railway Deploy. Секрети Railway `ADMIN_PASSWORD`, VAPID і налаштований порт змінювати не треба.

Адмінпанель тепер починається з окремого екрана **«Вхід для адміністратора»**. Серверний пароль перевіряється один раз на `/api/admin/login`; успішний вхід створює випадковий токен сеансу до 12 годин. Кнопка «Вийти» на `/api/admin/logout` анулює токен. Пароль не зберігається в JS між запитами, токен живе тільки в пам’яті поточної вкладки. При оновленні сторінки, перезапуску сервера або закінченні сеансу потрібно знову увійти.

Адреса Railway автоматично читається з наявного `push-config.json`; якщо його немає, натисніть «Налаштування сервера» на екрані входу та вкажіть HTTPS URL вручну.

Важливо: `APP_ORIGIN` на Railway має дорівнювати походженню GitHub Pages (`https://ваш-логін.github.io`) без шляху; приватний VAPID-ключ ніколи не публікуйте. Для керування файлами GitHub, як і раніше, потрібні `GITHUB_TOKEN` і `GITHUB_REPOSITORY`; для Push достатньо пароля.

# Тестові та власні Push із панелі адміністратора (v6.4)

Це оновлення працює з **тим самим Railway-сервером**, який уже налаштований для фонових Push. Нових VAPID-ключів генерувати **не потрібно**.

## Найпростіший запуск для існуючого сайту

1. Замініть файли на GitHub новими з архіву, зокрема `admin.html`, `admin.js`, `sw.js`, `push-server/server.js`, `push-server/admin.js` і **новим** `push-server/manual-push.js`.
2. Railway (де Root Directory = `/push-server`) зазвичай перебудує сервіс після нового коміту в GitHub. Переконайтеся у вкладці Deployments, що новий деплой `Active`. Якщо ні, зробіть Redeploy. Порт, URL, VAPID-ключі та Volume міняти не потрібно.
3. В Railway → Push-сервіс → Variables додайте **`ADMIN_PASSWORD`** зі своїм новим довгим паролем (мінімум 7 символів, краще 16+). **Не додавайте пароль до GitHub і не надсилайте його в чат.** Збережіть, застосуйте зміни.
4. Відкрийте `https://muzikmuzikant.github.io/svitlo-cherkasy/admin.html`, введіть HTTPS-адресу свого Railway і `ADMIN_PASSWORD`, натисніть **Увійти**.
5. У розділі **Push-повідомлення** виберіть **Лише цьому пристрою** → **Надіслати тестовий Push**. Якщо сторінку відкрито в Safari, а iPhone підписано в установленому PWA, можуть бути різні підписки. У цьому разі відкрийте панель усередині встановленого PWA або свідомо виберіть тест усім пристроям.
6. Щоб написати своє повідомлення: заповніть **Заголовок**, **Текст**, виберіть **Усі підписані** чи **конкретну підчергу**, перевірте попередній перегляд і натисніть **Надіслати власне повідомлення**. Для розсилки буде ще одне підтвердження.

- Для тестів і власних розсилок **не потрібен** `GITHUB_TOKEN`. Він потрібен лише для редагування файлів графіків через адмінпанель.
- Сервер перевіряє пароль, обмежує частоту розсилок, не віддає адреси Push-підписок і прибирає недійсні підписки.
- «Прийнято Push-службами» означає, що Apple/інший провайдер прийняв запит, а не гарантоване відображення на телефоні.
- Повідомлення може побачити будь-який користувач, який підписався на відповідну підчергу. Не надсилайте неперевірені «офіційні» повідомлення. Тестуйте спочатку на своєму телефоні.

# Фонові Web Push — окремий сервер (опційний)

GitHub Pages є статичним хостингом: **без цього компонента сповіщення на закритому iPhone не надходитимуть**. Додаток може показувати нагадування, поки відкритий, але Safari/iOS не гарантує точного таймінгу фонових задач.

1. Встановіть Node.js 20+. У `push-server` виконайте `npm install` і `npm run keys`, отримайте публічний і приватний VAPID-ключі.
2. Запустіть Node.js сервер на HTTPS-хостингу з **постійним сховищем** для `DATA_FILE` і без сну інстансу. Сервер опитує оновлений GitHub Pages JSON приблизно щохвилини. Хостинг може бути платним або мати обмеження безкоштовного тарифу.
3. Встановіть змінні середовища:
   - `VAPID_PUBLIC_KEY` = publicKey з генератора
   - `PUSH_PRIVATE_KEY` = privateKey з генератора
   - `PUSH_CONTACT` = `mailto:admin@example.com` (замініть на свій)
   - `APP_ORIGIN` = `https://YOURNAME.github.io`
   - `SCHEDULE_URL` = `https://YOURNAME.github.io/svitlo-cherkasy/data/schedules.json`
   - `DATA_FILE` = `/data/subscribers.json` (потрібен записуваний постійний диск)
   - `PORT` = порт сервера, наприклад `8787`
4. У корені PWA в `push-config.json` впишіть:
   `{"apiBase":"https://YOUR-PUSH-SERVER.example","publicKey":"YOUR_PUBLIC_VAPID_KEY"}`
5. Опублікуйте зміни в GitHub Pages. Встановіть PWA на головний екран iPhone, відкрийте **Опції → Дозволити та підписатися на Push**. Дозвіл запитується тільки після натискання.

У підписці передаються **тільки підчерга та налаштування типів сповіщень**, без адреси/імені. Підписка містить push endpoint (чутлива технічна інформація), тому не публікуйте файл `subscribers.json`. Рекомендується захистити endpoint додатково за потреби, контролювати навантаження й резервувати диск. Якщо змінити підчергу/налаштування, PWA оновлює запис. Реальні повідомлення надсилаються лише коли працездатний окремий сервер. Точна хвилина доставки не гарантується.

## Адмінпанель із паролем

Адмінпанель знаходиться у `admin.html` на сайті GitHub Pages. Щоб **справді редагувати й публікувати** дані, для того самого HTTPS-сервера потрібні ще три секрети:

- `ADMIN_PASSWORD`: пароль, який ви погодили для адмінпанелі (встановлений вами в Railway). **Використовуйте довгий унікальний пароль**, бо короткі паролі легко вгадати. Не публікуйте пароль у GitHub.
- `GITHUB_TOKEN`: fine-grained personal access token **лише для вашого репозиторію** з правами `Contents: Read and write`. Ніколи не вставляйте його в браузерний код або в `push-config.json`.
- `GITHUB_REPOSITORY`: у форматі `ваш-логін/svitlo-cherkasy`. Додатково `GITHUB_BRANCH=main`.

1. Додайте ці змінні середовища у налаштуваннях HTTPS-хостингу, де працює Node-сервер.
2. У GitHub Pages відкрийте `https://ваш-логін.github.io/svitlo-cherkasy/admin.html`.
3. Укажіть **HTTPS-адресу того ж push-сервера** та введіть адміністративний пароль.
4. Після входу можна відкрити редактор, перевірити зміни, підготувати уточнення адреси чи графіка, переглянути аварійні повідомлення, експортувати JSON і опублікувати його в GitHub через захищений сервер.
5. До публікації перевірте, що кожне уточнення має посилання на офіційне джерело. Зміни на GitHub Pages з'являються після нового розгортання.

Пароль перевіряється **на сервері**; у файлах PWA немає пароля й GitHub-токена. Без сервера панель дозволяє лише локальну діагностику, перевірку та експорт JSON. Для адміністративного API обов'язковий HTTPS. При невдалих спробах входу діє обмеження частоти.

> **Важливо:** пароль сам по собі не дозволяє правити GitHub Pages. Для цього сервер має мати токен репозиторію. Налаштування екстрених Push вимагає окремої й безперервної роботи того ж сервера. Не розміщуйте `subscribers.json`, `.env` та приватні ключі в публічному репозиторії.

## Доставка сповіщень на заблокований iPhone

Потрібні iOS 16.4+, Safari → «Поділитися» → «На початковий екран» для встановлення **саме вебзастосунку** (не просто вкладки Safari), HTTPS-сайт і сервер, який працює цілодобово. Після встановлення відкрийте застосунок з іконки → «Опції» → «Дозволити та підписатися на Push», підтвердьте системний дозвіл. Поставте потрібні перемикачі (відключення за 30 хв, повернення за 15 хв, оновлення графіка, завтра, екстрені повідомлення). Сповіщення можуть надходити на екран блокування, але iOS і мережа визначають точний момент доставки.

Сервер використовує підписку Web Push (endpoint та ключі шифрування) й вашу підчергу; повна адреса користувача не передається. **GitHub Actions не замінює постійно запущений Web Push сервер**, а лише збирає публічні графіки.

## Звернення користувачів (v6.9.0)

Новий публічний endpoint `POST /api/feedback` приймає коротке текстове звернення з темою `bug` / `address` / `idea` / `other` й необов'язковою електронною поштою. Дозволений тільки `Origin`, що дорівнює `APP_ORIGIN`. Реєстрація та Push-підписка не потрібні. Система має базовий захист від спаму: до 3 звернень на IP за 15 хвилин, обмеження розміру й honeypot. Для масштабного запуску рекомендується додатковий антибот-захист.

За замовчуванням звернення зберігаються в `feedback.json` поруч із `DATA_FILE`. Наприклад, якщо `DATA_FILE=/data/subscribers.json`, збереження йде в `/data/feedback.json` на тому самому Railway Volume. За потреби можна задати `FEEDBACK_FILE=/data/feedback.json` у Railway Variables. **Не** додавайте цей JSON у GitHub. Дані очищаються через 90 днів. Зберігаються текст, тема, статус, час, optional email; адреса IP у файлі не зберігається.

Увійдіть до `admin.html` за `ADMIN_PASSWORD`, потім використайте «Звернення користувачів». Доступні `GET /api/admin/feedback`, `PATCH /api/admin/feedback/{id}`, `DELETE /api/admin/feedback/{id}` тільки з дійсним токеном адмінсеансу. Для цих операцій не потрібен `GITHUB_TOKEN`.
