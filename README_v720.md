# Світло Черкаси v7.2.0 — комплексна стабілізація

## Встановлення на чинний сайт

1. У репозиторії GitHub натисніть `Code → Download ZIP` для резервної копії.
2. Вміст `svitlo-cherkasy-v7.2.0-update.zip` завантажте **у корінь репозиторію**, зі збереженням `.github/workflows`, `scripts`, `push-server` та решти підпапок.
3. У архіві **немає** `data/addresses.json`, `data/schedules.json`, `data/manual_overrides.json`, `data/published_street_fallback.json`, `data/emergency.json`, `data/source_review.json`, `push-config.json`, `CNAME` або іконок. Не видаляйте ці файли з GitHub.
4. `Commit changes`. Перевірте зелені `Code and Data Checks` (ручний запуск), `Publish Svitlo Cherkasy PWA`.
5. У `Actions → Update official blackout data → Run workflow` запустіть імпортер вручну. Переконайтеся, що графік збігається з офіційною публікацією. В `Actions → Refresh official address queues` можна окремо перевірити PDF-адреси.
6. Якщо Railway підключений до GitHub (root `/push-server`), дочекайтеся його деплою і перевірте `/health` та Push. Наявні Railway Variables не змінюйте.
7. У встановленому PWA відкрийте `Опції → Перевірити оновлення застосунку`.

**Важливо:** локальні тести не перевіряють живу правильність Черкасиобленерго та не доводять, що GitHub Actions і Railway запрацюють саме у вашому розгортанні. При невдалому імпорті **не надсилайте графікові Push**; графіки потрібно звіряти з оператором.

## Що змінено

- `scripts/update_data.py`: обмежені повторні HTTP-запити для 429/5xx, підтримка запису часу `з 14:00 до 16:00`, пріоритет порядку нових публікацій при однакових часових мітках, явні `confirmedNoScheduleDates`, захист від масової втрати адрес після зміни формату PDF, збереження назви населеного пункту.
- `.github/workflows/update.yml`: перевірка офіційних графіків кожні 5 хв за розкладом; додаткові регресійні тести та журнал перевірки; справжні зміни публікуються негайно, незмінний heartbeat — через 30 хв. GitHub може затримувати cron.
- `.github/workflows/update-addresses.yml`: перевірка адресних PDF щодня (раніше щотижня), сувора відмова від неповної або різко обірваної бази.
- `.github/workflows/emergency.yml`, `scripts/emergency_gate.py`: перевірка аварійних повідомлень кожні 5 хв; незмінний стан не запускає сотні повторних деплоїв — heartbeat раз на годину.
- `data-merge.js`: свіжий адресний перелік **замінює**, а не механічно зливається зі старими підказками; резервний перелік використовується, коли офіційні записи для населеного пункту взагалі відсутні. Ручні перевірені адміністратором уточнення окремі.
- `address-lookup.js`, `app.js`: точні номери і вуличні підказки не змішуються; варіанти номерів та результати уточнень зрозумілі; автоматично додаються населені пункти з актуального офіційного адресного імпорту; непідтверджені підчерги не вгадуються; статус застарілих даних помітний через ~55 хв без перевірки.
- `push-server/schedule-engine.js`, `push-server/server.js`: коли підтверджений графік пропускає підчергу, для неї немає планових відключень; перевірка актуальності графіка перед плановими нагадуваннями; нагадування за 30 хв працює на межі 23:30→00:00; натискання на Push відкриває адресу PWA `APP_ORIGIN`, а не сирий JSON.
- `install.js`, `sw.js`, `scripts/build_pages.py`, `release.json`: узгоджена реєстрація нового JS-модуля, кеш і версія 7.2.0. Іконки iOS не змінювалися.

## Обмеження, які не можна приховувати

- Для сіл, де оператор оприлюднив лише вулицю і кілька підчерг **без номерів будинків**, ми фізично не можемо достовірно визначити підчергу конкретного будинку. Потрібна перевірка в оператора або вибір **вже відомої користувачеві** підчерги.
- Відсутність планового графіка означає **відсутність оголошених планових відключень**, а не гарантію фактичного електропостачання.
- GitHub Actions не гарантує запуск рівно кожні 5 хв; Railway і GitHub Pages можуть додавати затримку до появи правок і Push.
- Значне реорганізування GitHub/Railway/Supabase під час цього релізу не проводилося; це сумісне стабілізаційне оновлення, а не повна заміна архітектури.
