## 15 правил, що мають пріоритет

1. **НІКОЛИ не змішуй Beta з Production.** Production: `main`, `https://svitlo-cherkasy.pp.ua`, Railway `https://svitlo-cherkasy-production.up.railway.app`. Beta: гілка `staging`, `https://svitlo-cherkasy.pages.dev`, окремий Railway `https://svitlo-beta-api-staging.up.railway.app`. Для тестів створюй гілку від актуального `staging`; тільки після тестів готуй окремий release PR від **актуального** `main` із вибірковим перенесенням. **Не зливай і не публікуй у production без прямої команди власника.**
2. **Перед кодом перевір живий стан GitHub і відповідного деплою.** Документація є історичним знімком від 20.10.2026; не видавай її за доказ нинішнього стану. `main` на момент написання: `release.json` 7.9.10, `staging` 7.9.13. Перевіряй заново.
3. **Не роби вигляд, ніби виправив баг.** Називай конкретну причину, змінені файли, тести, branch/commit/PR та що реально перевірено. Не кажи «готово», якщо файл не записаний у GitHub або немає успішного тесту.
4. **Основний користувач має iPhone.** iOS Safari + встановлений PWA в пріоритеті: жодного горизонтального скролу/zoom, ривків вкладок, подвійного натискання, зламаних safe areas, старих кешів чи «мертвого» запуску.
5. **Дизайн преміального рівня, світла тема, акуратні векторні іконки, плавні мікроанімації на ВСІХ нових доречних діях, включно з закриттям.** Заборонено замінювати чинні значки на випадкові символи/емодзі. Читай `DESIGN_RULES.md`.
6. **Ніколи не використовуй довге тире «—» у публічних текстах застосунку, в банерах оновлень чи у спілкуванні з власником.** Пиши природною українською, без канцеляриту, шаблонного ШІ-тону та девелоперського жаргону для звичайних користувачів.
7. **Якщо для дати відсутній опублікований плановий графік, у PWA показувати «Світло весь день» і 24 зелені години.** Це навмисне незмінне правило; читай `SCHEDULE_DISPLAY_CONTRACT.md`. Воно описує ПЛАНОВИЙ графік, не фізичну напругу у будинку. Не змінюй без прямо висловленої волі власника.
8. **Адресна книга та визначення електричної підчерги є РІЗНИМИ задачами.** Вулиці мають бути доступні для пошуку незалежно від наявності даних про електричну мережу. Не вигадуй підчерг із OSM/GIS. Якщо офіційне джерело містить лише вулицю з однозначною підчергою, не вимагай будинок; якщо офіційно розділені будинки, не приписуй усій вулиці одну підчергу. Точні будинки не вгадувати.
9. **Звернення користувачів і сповіщення мають бути синхронізованими.** Видалення, приховування, закріплення й редагування в адмінці мають бути видимі в користувача без перезапуску, з авторитетним серверним станом, очищенням локального кешу та акуратними анімаціями.
10. **Web Push працює з сервером, а не магією JavaScript.** Потрібні повідомлення при закритому встановленому PWA; **одна подія = одне сповіщення**, дедуплікація на сервері, у service worker та Inbox. НІКОЛИ не надсилай масовий тестовий Push користувачам без явного дозволу.
11. **Не руйнуй live-дані.** Не перезаписуй живі `data/*.json` старим станом із `staging`, не скидай Railway volume `/data`, не змінюй VAPID-пару, `CNAME`, production `push-config.json`, `manifest.webmanifest` чи Google verification без окремо перевіреного плану.
12. **На Production реклама вимкнена до окремого схвалення; добровільна підтримка проєкту НЕ повинна вимикатися разом із рекламою.** Ніколи не вмикай рекламні покази самовільно. Приватні ключі, паролі, токени, дані звернень, Push-підписки не потрапляють у репозиторій або публічний сайт.
13. **Публічний банер оновлення = можливості для користувача.** Ніяких слів «сервер», «бекенд», «Socket», «адмінка», «API», «релізний пайплайн». Якщо зміни технічні: «Виправлення помилок».
14. **Власник НЕ хоче виконувати розробку руками.** Якщо інструменти дають GitHub/Railway-доступ, працюй сам: діагностика, код, тести, коміти, PR. Якщо власнику потрібен крок, дай найпростіші покрокові інструкції для початківця з iPhone, точні назви кнопок і перевірки.
15. **Працюй до повного результату у межах доступних інструментів.** Не зупиняйся після красивого плану. Не обіцяй асинхронну роботу без справжньої задачі. Проводь регресійні тести й перевіряй, чи не повернулись старі проблеми.

## Мінімальний цикл для кожного завдання

`Поточний стан → корінь проблеми → окрема гілка від staging → точкова зміна + регресійний тест → Python/Node/збірка → перевірка Beta → підсумок з посиланнями → окреме схвалення Production`.

У великих завданнях роби важливі результати одразу й звітуй факти, а не задавай десятки уточнень. Якщо немає доступу до реального iPhone або Railway, явно відокремлюй unit-тести від неперевірених ручних перевірок. Якщо новий запит суперечить цим правилам, остання **пряма** вказівка власника має пріоритет; зафіксуй оновлене правило в документації.
